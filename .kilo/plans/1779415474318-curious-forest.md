# Plan: Revamp safe-code Skills with Six-File Context Methodology

## Source Material

- YouTube transcript: JSM "How Senior Engineers Actually Build With AI in 2026"
- `Six-File+Context+Methodology.zip` — blank templates + README playbook
- `01 — How Real Engineers Build` zip — Ghost AI real-world context files + feature specs

## Core Insight

The six-file system and safe-code solve **different problems** that complement each other perfectly:

```
Six-File System  →  project context  (what we're building, written once, updated rarely)
safe-code docs   →  session state    (where we are, updated every session)
```

The six-file system prevents **agent drift** across sessions by giving every new agent full architectural context before it touches code. safe-code prevents **context loss** within and between sessions by maintaining a live session diary and resume point.

Together they cover the full lifecycle:

```
Before first prompt:   context/ files define the system
Every session start:   AGENTS.md → context/ → ACTIVE.md → SESSION.md
During session:        SESSION.md tracks work, LOG.md records decisions
End of session:        /safe-code --save commits + migrates to ACTIVE.md
Next session:          /safe-code or /safe-code --continue auto-resumes saved context when ACTIVE.md exists
```

---

## Decisions

| Question | Answer |
|---|---|
| How is `context/` created? | Auto by `/safe-code` on first run |
| `progress-tracker.md` vs `ACTIVE.md` | Keep both — different audiences |
| Feature spec authoring | AI writes feature specs from user intent + existing context before implementation |
| Existing projects | `/safe-code` first audits current repo, then backfills context from evidence without inventing missing facts |
| Old safe-code projects | Auto-migrate old continuity-only setup into new `context/` methodology without losing old docs |
| Forgetting `--continue` | `/safe-code` auto-detects saved state and resumes unless user explicitly asks for fresh setup |
| Writes before `--save` | Persistent context/doc sync is drafted in `SESSION.md`; final context/continuity writes happen on `/safe-code --save` unless a file is required for immediate work |

**Why keep both progress-tracker and ACTIVE.md:**
- `context/progress-tracker.md` = project-level persistent record. Any agent, any tool, any session reads it to understand where the project stands.
- `.codex/agents/ACTIVE.md` = session-scoped resume point. safe-code writes it on `--save`, reads it on `--continue`. It's operational state, not project history.

## What Changes

### 1. `skills/safe-code/SKILL.md`

**Doc structure** — add `context/` folder:

```
<project-root>/
├── AGENTS.md                      ← entry point (reads context/ in order)
├── CHANGELOG.md                   ← release history
├── context/                       ← NEW: six-file project context
│   ├── project-overview.md        ← what, who, goals, scope, success criteria
│   ├── architecture.md            ← stack, boundaries, storage, invariants
│   ├── code-standards.md          ← TypeScript/framework conventions
│   ├── ai-workflow-rules.md       ← how the agent should behave
│   ├── ui-context.md              ← design tokens, component conventions
│   ├── progress-tracker.md        ← current phase, decisions, session notes
│   ├── current-issues.md          ← local-only manual user scratchpad for bugs/errors
│   └── feature-specs/             ← focused build specs, one unit per file
│       ├── 01-design-system.md
│       └── 02-editor.md
└── .codex/agents/                 ← session management (unchanged)
    ├── ACTIVE.md                  ← persistent state + resume point
    ├── SESSION.md                 ← working memory RAM (wiped on save)
    ├── LOG.md                     ← append-only diary
    ├── BACKLOG.md                 ← task queue
    ├── MEMORY.md                  ← architecture snapshot
    └── safe-refactor-code.md      ← refactor rules + flagged code
```

**Step 1 changes:**
- After creating continuity docs, scaffold `context/` with blank templates if missing
- Never overwrite existing `context/` files
- Add `context/` creation to the Step 1 confirmation output
- Treat `context/` files as thin/missing the same way `AGENTS.md` is treated — if they exist but are empty stubs, populate them from repo investigation
- Create `context/feature-specs/` if missing
- Create `context/current-issues.md` if missing and add `/context/current-issues.md` to `.gitignore`
- `context/current-issues.md` is manually written by the user, not AI-generated project context. It is a local-only debugging scratchpad and must not be committed.
- If project is already in progress or done, run an evidence-first backfill: inspect README, manifests, routes, schemas, tests, configs, and existing docs before populating context files. Do not rewrite architecture from assumptions.
- If project facts cannot be proven from repo evidence, add them to `context/progress-tracker.md` under Open Questions instead of inventing them.
- For existing projects, generate feature specs only for new work, active bugs, refactors, or missing documentation units. Do not attempt to create a retroactive spec for every completed feature unless user asks.

**Old safe-code migration behavior:**
- Detect old-method projects by existing `.codex/agents/ACTIVE.md`, `SESSION.md`, `LOG.md`, `BACKLOG.md`, `MEMORY.md`, or `safe-refactor-code.md` with no `context/` folder.
- Do not delete old continuity docs during migration.
- Read old docs as source material, then draft mappings into new context files:
  - `MEMORY.md` → `context/architecture.md` candidate facts
  - `BACKLOG.md` → `context/progress-tracker.md` Next Up / Open Questions
  - `ACTIVE.md` → `context/progress-tracker.md` Current Goal / In Progress
  - `LOG.md` → `context/progress-tracker.md` safe decision summaries only
  - existing `AGENTS.md` → preserve project rules and add Read First section
- Never copy raw logs, secrets, stack traces, private URLs, or `current-issues.md` content into context files.
- Mark uncertain migrated facts as Open Questions, not truth.
- Store the migration draft in `SESSION.md` first. Apply final migrated context files only on `/safe-code --save`, except missing scaffold files may be created immediately.
- After successful `/safe-code --save`, keep old continuity docs active for session state, but treat `context/` as the canonical project context going forward.

**Auto-continue behavior:**
- If user runs `/safe-code` and `.codex/agents/ACTIVE.md` exists with unfinished work, automatically behave like `/safe-code --continue`.
- Print a short note: `Saved safe-code session found; resuming automatically. Say "fresh pass" to ignore saved state.`
- Only start fresh setup when no saved state exists or user explicitly asks for fresh setup/full new pass.
- This prevents context loss when users forget `--continue`.

**Write timing behavior:**
- During normal work, keep proposed updates to `context/*.md`, `AGENTS.md`, `CHANGELOG.md`, and continuity docs as draft notes in `.codex/agents/SESSION.md`.
- Apply those documentation/context updates on `/safe-code --save`.
- Exception: create missing scaffold files/folders needed for safe operation (`AGENTS.md`, `context/`, `context/feature-specs/`, `.codex/agents/`, `.gitignore` entry for `/context/current-issues.md`) during setup if absent.
- Exception: write an active feature spec before implementation when the user asks for feature work, because the spec is the work contract.
- Never write `context/current-issues.md` content automatically; only create blank template if missing.

**Helper skill behavior:**
- `safe-code` may call helper skills (`codebase-pruner`, `safe-refactor-code`, `review-changes`, `debug-issue`, `build-graph`, `explore-codebase`) internally.
- Helper skills must not make broad changes automatically just because `/safe-code` ran.
- `codebase-pruner` runs in analysis mode first, lists candidates, and removes only items with evidence and within selected cleanup/refactor scope.
- `safe-refactor-code` runs only when refactor scope exists from user request, feature spec, cleanup profile, or verified pruner finding.
- All helper outputs feed the safe-code task list and `SESSION.md` drafts; final context/doc sync waits for `/safe-code --save`.

**`AGENTS.md` template update:**
- Change the template to be a lean entry point that lists the six context files to read in order (mirrors Ghost AI's `AGENTS.md` pattern)
- Keep the high-signal project facts section (exact commands, env vars, gotchas) — these don't belong in `context/` files
- The new shape:

```md
# AGENTS.md

## Read First
Read the following files in order before implementing or making any architectural decision:
1. `context/project-overview.md` — product definition, goals, features, and scope
2. `context/architecture.md` — system structure, boundaries, storage model, and invariants
3. `context/ui-context.md` — theme, colors, typography, and component conventions
4. `context/code-standards.md` — implementation rules and conventions
5. `context/ai-workflow-rules.md` — development workflow, scoping rules, and delivery approach
6. `context/progress-tracker.md` — current phase, completed work, open questions, and next steps
7. Active spec in `context/feature-specs/` when implementing a feature

Do not read `context/current-issues.md` unless the user explicitly asks you to debug/fix an issue or references that file. It is manually written by the user and may contain secrets, tokens, stack traces, private URLs, or raw logs.

Update `context/progress-tracker.md` after each meaningful implementation change.

## Feature Specs

- Feature specs live in `context/feature-specs/`.
- AI may draft feature specs from user intent, repo evidence, and context files.
- Do not implement a feature until there is an active spec, unless the user explicitly asks for a tiny direct edit.
- For new projects, create specs in planned build order: `01-design-system.md`, `02-editor.md`, etc.
- For existing or in-progress projects, create specs only for upcoming work or unclear areas. Do not rewrite completed history.
- Each spec must include goal, scope, files/areas likely touched, acceptance checks, and out-of-scope items.

## Session State
Read before resuming any safe-code session:
- `.codex/agents/ACTIVE.md` — current task + resume point
- `.codex/agents/SESSION.md` — working memory (carry forward only)

## Project Facts
<!-- High-signal facts that don't fit in context/ files -->
<!-- Exact commands, env vars, gotchas, non-obvious setup -->

## Tech Stack
- Runtime:
- Framework:
- Database:
- Other:

## Environment
- Dev command:
- Build command:
- Test command:
- Package manager:
```

**Loading layers update:**
- Layer 1 now includes `context/progress-tracker.md` (index read — current phase + next steps only)
- Layer 2 (`--continue`) loads full `context/progress-tracker.md`
- Layer 3 (audit/refactor) loads `context/architecture.md` alongside `MEMORY.md`

**Step 2 (Load Context) update:**
- After loading `AGENTS.md`, load `context/progress-tracker.md` (current phase + next steps block only)
- On `--continue`, load full `context/progress-tracker.md`

**Step 7 (Sync Docs) update:**
- Add `context/progress-tracker.md` to the sync table: update when phase changes, feature completes, or architectural decision is made
- Distinguish: `MEMORY.md` = session architecture notes; `context/progress-tracker.md` = project-level phase + decision log

### 4. New skill: `skills/spec-writer/SKILL.md`

A standalone skill for writing feature spec files following the JSM pattern. Works for any project, not just safe-code users.

**Trigger phrases:** "write a spec", "create a feature spec", "spec out this feature", "write a spec file", `/spec-writer`

**What it does:**
1. Reads `context/project-overview.md` and `context/architecture.md` if they exist
2. Asks the user what feature/unit to spec (or accepts it as input)
3. Has a short planning conversation to clarify goal, design decisions, implementation boundaries, and verification conditions
4. Produces a spec file following the JSM pattern

**Spec file pattern:**
```md
# Unit NN: [Feature Name]

## Goal
<!-- 1-2 sentences. Concrete output when this unit is complete. -->

## Design
<!-- Visual and structural decisions. Reference ui-context.md tokens. -->

## Implementation

### [Component or Sub-section]
<!-- What to build and how. No ambiguity about done. -->

## Dependencies
- <!-- package-name (reason) -->

## Verify When Done
- [ ] <!-- Specific condition -->
- [ ] No TypeScript errors
- [ ] No console errors
- [ ] `npm run build` passes
```

**Skill behavior:**
- Reads existing context files to avoid asking questions already answered there
- Asks only what's missing: goal, design decisions, implementation sub-sections, verification conditions
- Writes the spec file to `context/feature-specs/NN-feature-name.md` (creates `context/feature-specs/` folder if missing)
- Updates `context/progress-tracker.md` Next Up section with the new spec
- Prints the one-liner prompt to give the coding agent: `Read context/feature-specs/NN-feature-name.md. Update context/progress-tracker.md to mark this in progress. Implement exactly as specified. Do not go beyond scope.`
