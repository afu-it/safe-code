# v4.8 Design Spec — `/safe-code --graphify` (knowledge-graph mode)

*Date: 2026-07-26 · Status: implemented — Tier 2 shipped as v4.8; Tier 1 (`--graphify` orchestration) shipped as v4.9*
*Source study: https://github.com/Graphify-Labs/graphify (cloned + read: README, ARCHITECTURE.md, docs/how-it-works.md, graphify/skill.md 702 lines)*

## What graphify is

`/graphify` turns any folder (code, docs, PDFs, images, video) into a persistent knowledge graph you query instead of grepping. Backed by a Python package (`graphifyy` on PyPI); the skill orchestrates the CLI. Outputs land in `graphify-out/`: `graph.html` (interactive viz), `GRAPH_REPORT.md` (plain-language highlights), `graph.json` (queryable, persistent).

## Ideas worth stealing (ranked)

1. **Two-tier extraction.** Code is parsed deterministically (tree-sitter AST — free, local, no LLM); only docs/papers/images get an LLM semantic pass. A code-only corpus costs zero tokens. *Lesson for safe-code: prefer deterministic evidence, spend LLM only where structure can't reach.*
2. **Confidence audit trail on every edge.** `EXTRACTED` (explicit in source, confidence 1.0) vs `INFERRED` (discrete rubric 0.55–0.95) vs `AMBIGUOUS` (flagged for human review). *This is the graph version of safe-code's "never invent facts" — and portable to our context files.*
3. **Fast-path query rule.** If `graph.json` exists and the user asks a natural-language question, skip the whole pipeline and query the graph immediately — no re-detect, no re-build. *Same shape as our auto-resume: saved artifact short-circuits work.*
4. **Graph structure instead of embeddings.** Leiden community detection over extracted edges; no vector DB. Communities become report sections and navigation units.
5. **Parallel subagent fan-out with hard mechanics.** Chunk 20–25 files, group by directory, dispatch ALL agents in one message, chunk-file-on-disk = success signal, >50% chunks failed = abort with instructions. *More rigorous than our Helper Execution Mode; worth back-porting the success-signal + majority-fail rules.*
6. **Extraction cache keyed by the prompt file.** Prompt upgrade invalidates old cache entries; stale cache files are deleted, never merged. *Same idea as our `last_synced_commit` stamp, applied to LLM output.*
7. **Report as invitation.** `GRAPH_REPORT.md` leads with god nodes (most-connected concepts), surprising cross-document connections, and *suggested questions* — it teaches the user what to ask next.
8. **Interpreter/state persistence.** Detected Python path + scan root written to dot-files inside the out-dir so every later step and session reuses them. Robust uv/pipx/shebang detection.
9. **Security layer.** URL validation, out-dir path confinement, label sanitization, sensitive-file skip *with visible report* (so a wrongly-flagged file is noticed).
10. **Read-only graph health gate** before reporting, and honest cost/timing estimates printed *before* dispatching agents.

## What we build: `/safe-code --graphify`

**Decision: orchestrate, don't reimplement.** safe-code is prompt-engineered Markdown; graphify is a real Python pipeline. Rebuilding tree-sitter extraction in prose is impossible. So `--graphify` follows the existing Step 3f pattern (code-review-graph): detect → bootstrap → orchestrate → graceful fallback. Two integration tiers:

### Tier 1 — orchestrate the graphify pipeline (the mode itself)

```
/safe-code --graphify              build/refresh the project knowledge graph
/safe-code --graphify "<question>" query the existing graph (fast path, read-only)
```

Behavior:

1. **Command Recognition**: add `--graphify [question]` to the argument map. Bare `--graphify` -> build mode; with a quoted trailing argument -> query mode.
2. **Detect access order**: `$graphify` skill installed on host -> dispatch it as a helper (`$graphify` joins the helper table) · `graphify` CLI on PATH -> drive the CLI · `uv`/`uvx` available -> offer install (see safety) · none -> record `Graphify: unavailable`, suggest `uv tool install graphifyy`, continue without.
3. **Build mode** runs the pipeline on the project root, then harvests for the brain (all draft-until-save):
   - `GRAPH_REPORT.md` god nodes + communities -> `architecture.md` Navigation map refresh.
   - Surprising connections + suggested questions -> `progress-tracker.md` Open Questions candidates.
   - Graph stats (`files/nodes/edges/communities`) -> Step 8 banner `Graph:` line.
   - God-node list -> seeds for the Context Self-Test question set (ask about the most-connected concepts first).
4. **Query mode** is read-only like `--explain`: run `graphify query`, relay the scoped subgraph answer, change nothing, commit nothing.
5. **Freshness tie-in**: when a graph exists, prefer graph delta over `git diff --stat` for the Context Freshness drift scan (extends the existing rule that already prefers `detect_changes_tool`).
6. **Fast-path rule for consumers**: the AGENTS.md template gains one line — "If `graphify-out/graph.json` exists, answer codebase questions by querying it before grepping." (Mirrors graphify's own fast path; costs one sentence.)

Safety mapping (all existing invariants hold):

- `graphify-out/` lives inside the project root and is **gitignored** via its own `.gitignore`, exactly like `.code-review-graph/`. Never committed by `--save`.
- **No silent installs**: Step 3f's "never run installs automatically" stands. The `--graphify` flag is explicit user intent, but the first install still asks once (a PyPI package is a supply-chain decision — same posture as Step 4b) and records the answer in `user-preferences.md`.
- Semantic extraction reads docs — the Safety Invariants gate what may be quoted into committed files; `current-issues.md` content never enters the graph corpus (add it to the skip list).
- `--graphify` never pushes, never commits; build artifacts are not session state.

### Tier 2 — adopt the ideas natively (no dependency needed)

These land in safe-code prose regardless of whether graphify is installed:

1. **Evidence tags in the brain.** Context-file claims may carry `[extracted]` (verifiable command/path cited) vs `[inferred]` (deduction — must name what it's deduced from). The Context Self-Test grades `[inferred]`-only answers as weaker. This is idea #2 applied to our actual product: the brain gets graphify's honesty labels without its graph.
2. **Subagent mechanics hardening** (Helper Execution Mode): result-file-on-disk as the success signal for write-capable subagents, and the >50%-failed abort rule.
3. **Report-as-invitation**: the Step 8 summary's `Follow-up` line may include 1–2 *suggested questions* the run surfaced, not just pending tasks.

## Decisions (2026-07-26, user delegated to recommendation)

1. **Keep both graphs, side by side.** `code-review-graph` stays for refactor impact / dead-code (Steps 4–6); graphify covers project understanding + query. They are not substitutes — replacing would lose `refactor_tool` capability for nothing in return. v4.9 must add one clear "which graph when" paragraph to Step 3f.
2. **Minimal query surface for v1.** Only `/safe-code --graphify` and `/safe-code --graphify "<question>"`. No `path`/`explain` passthroughs — the agent running the query may use them internally; the user never needs to know the flags exist. Keeps Command Recognition small (compliance-drift protection from v4.7).
3. **Split.** Tier 2 (evidence tags, subagent success-signal + majority-fail hardening, "Worth asking next" summary line) shipped as **v4.8** — zero-dependency, strengthens the core for every user, small enough to dogfood quickly. Tier 1 graphify orchestration is **v4.9**: it depends on an external, fast-moving PyPI package and must not hold the safe wins hostage.
